## E0 — Qué es E2E aquí y qué queda fuera

- **E2E = el proceso real** (`src/server.ts`: dos puertos, jobs y timeouts) arrancado como hijo, hablando **HTTP de verdad**
  con `fetch`, con **cookies y cabecera `Origin` como un navegador** y **sobre los datos HIS reales importados**.
  Nada de supertest ni de `createApp()` en memoria: eso ya lo cubren los 481 tests de integración.
- **Fuera de alcance (lo decidió el usuario):** todo lo que envía correo (verificación, reset de contraseña, avisos de
  seguridad) y el chat (`POST /assistant/query` y la API interna del agente). Tampoco se prueba Redis (no hay Redis local).
- **Verificación independiente:** cada cifra de la API se coteja con una consulta propia del test (Prisma o `$queryRaw` en el
  test, escrita desde cero, nunca importando servicios de `src/`) o con los archivos crudos de `data/raw/`. Un test que solo
  compruebe `status === 200` no vale: comprueba forma, tipos y valores.
- Los tests son **idempotentes y relanzables** sobre la misma BD: correos únicos por corrida (`e2e-<ts>-<n>@e2e.test`) y cada
  archivo deja su estado mutable como lo encontró (stock, alertas que toca, roles propios). Nunca asumas un conteo global de
  alertas o de auditoría: filtra por lo que tu test creó (ids, `requestId`, marca de tiempo).

## E1 — Infraestructura (la crea T12; el resto la consume)

- `vitest.e2e.config.mts`: `include: ['tests/e2e/**/*.e2e.test.ts']`, `fileParallelism: false`, `testTimeout: 60_000`,
  `hookTimeout: 180_000`, `globalSetup: ['tests/e2e/global-setup.ts']`, **sin** `setupFiles` (no hereda los valores de test).
  En `vitest.config.mts` se añade `exclude: ['tests/e2e/**']` para que `npm test` no los ejecute.
- `package.json`: `"test:e2e": "vitest run --config vitest.e2e.config.mts"`.
- Variables de la corrida (con valores por defecto): `E2E_DATABASE` (`hospital_e2e`) y `E2E_PORT` (`3200`; el interno es `E2E_PORT+1`).
  La URL de la BD se construye cambiando el nombre de la base en la `DATABASE_URL` de `.env` (leída con `process.loadEnvFile`).
- **`tests/e2e/global-setup.ts`:** (1) `prisma migrate deploy` sobre la BD E2E (nunca reset); (2) seed
  (`npx tsx prisma/seed.ts`, con `PASSWORD_BREACH_CHECK=false` y `MAIL_ENABLED=false`); (3) `npm run data:import` **solo si**
  `his_admissions` está vacía; (4) limpia el estado de corridas anteriores: usuarios `@e2e.test` (sesiones, cuentas, roles de
  usuario), roles no-sistema cuyo nombre empiece por `e2e-`, todo `medication_stock` y todas las `alerts` (la auditoría es
  append-only: no se toca); (5) arranca el servidor con `iniciarServidor` y guarda la URL con `provide()`; (6) en el teardown lo para.
- **`tests/e2e/servidor.ts`:** `export async function iniciarServidor(opts: { puerto: number; env?: Record<string,string> }): Promise<{ url: string; internalUrl: string; detener(): Promise<void> }>`.
  Lanza `node --import tsx src/server.ts` (o `npx tsx`) con `NODE_ENV=development`, `PORT`, `INTERNAL_PORT`, `API_URL`,
  `DATABASE_URL` de la BD E2E, `MAIL_ENABLED=false`, `PASSWORD_BREACH_CHECK=false`, `LOG_LEVEL=warn`, sin `AGENT_URL`, y lo
  que pase `opts.env`. Espera a `GET /api/v1/health/ready` = 200 con reintentos (máx. 60 s) y, si el proceso muere, lanza un
  error con las últimas líneas de su salida. `detener()` manda SIGTERM, espera la salida y, si no llega, SIGKILL.
  El servidor funcional se arranca con límites altos (`RATE_LIMIT_MAX`, `AUTH_RATE_LIMIT_MAX`, `AUTH_SIGNIN_MAX` y
  `AUTH_MFA_MAX` = 100000): los límites reales se prueban aparte, en un servidor propio.
- **`tests/e2e/cliente.ts`:** cliente mínimo sobre `fetch`:
  ```ts
  export const ORIGEN = 'http://localhost:5173';
  export class Sesion {          // una instancia por usuario; guarda la cookie de sesión como un navegador
    constructor(base: string);
    login(email: string, password: string): Promise<Response>;   // POST /api/v1/auth/sign-in/email
    get(ruta: string): Promise<Respuesta>; post/put/patch/delete(ruta, body?): Promise<Respuesta>;
    raw(ruta: string, init: RequestInit): Promise<Response>;      // sin tocar cabeceras, para CSRF/415/CORS
  }
  export interface Respuesta { status: number; headers: Headers; body: any /* JSON parseado o texto */ }
  export async function comoRol(base: string, rol: string): Promise<Sesion>   // crea (vía superadmin y POST /users) un usuario @e2e.test con ese rol y devuelve su sesión
  export const credenciales: { superadmin; director; farmacia } // de .env (SEED_*) o de los valores por defecto de env.ts
  export function prismaE2E(): PrismaClient                    // cliente contra la BD E2E, para cotejar
  ```
  Todas las peticiones llevan `Origin: ORIGEN` y la cookie de la sesión (`Sesion.raw` no añade nada).
  Si ves que `any` choca con CLAUDE.md §11, usa `unknown` y helpers de acceso: el lint se aplica también a los tests.
- Una spec de humo, `tests/e2e/salud.e2e.test.ts` (ver T12), que demuestra que la infraestructura funciona.

  `https://evil.example` → sin `Access-Control-Allow-Origin`.
- El puerto público no sirve `/internal/agent/query` (404) y el puerto interno sin clave responde 401 (la única prueba del
  puerto interno: el resto del chat está fuera de alcance).
- Arranque/parada limpios: tras el teardown los dos puertos quedan libres.

## T13 — Autenticación, sesiones, 2FA, CSRF y límites (ola E2)

`tests/e2e/auth.e2e.test.ts` y `tests/e2e/limites.e2e.test.ts`:
- Login de superadmin, director y farmacia → 200, cookie de sesión `HttpOnly` + `SameSite=Lax`; `GET /auth/get-session` y
  `GET /users/me` (roles y permisos efectivos exactos según `SYSTEM_ROLES`); contraseña incorrecta → 401 con el mismo mensaje
  para un correo inexistente (sin enumeración); auditoría `auth.login.success`.
- Bearer: la cabecera `set-auth-token` del login sirve como `Authorization: Bearer` sin cookie.
- Logout → la cookie queda invalidada (la siguiente petición da 401) y se audita `auth.logout` con ip/userAgent.
- Registro público bloqueado: `POST /auth/sign-up/email` → 403.
- CSRF: una petición mutante con cookie y sin `Origin` → 403; con `Origin` no permitido → 403; con el correcto → pasa.
- 415 con `text/plain`; JSON malformado → 400; cuerpo por encima de `BODY_LIMIT` → 400.
- Cambio de contraseña (`/auth/change-password`) → la nueva funciona, la vieja no, y se restaura al final.
- 2FA TOTP de punta a punta sobre un usuario `@e2e.test`: enable → verify con un TOTP calculado en el test (HMAC-SHA1
  RFC 6238, con `node:crypto`, unas 15 líneas) → el login exige segundo factor → verify-totp → sesión; un código incorrecto → rechazo; disable.
- Cuenta suspendida (PATCH `status` como admin): la sesión abierta pasa a 403 `ACCOUNT_SUSPENDED` y un login nuevo no abre
  sesión; reactivada vuelve a entrar. Borrado lógico → no puede entrar y deja de salir en `GET /users`.
- `limites.e2e.test.ts` arranca **su propio servidor** con los límites por defecto de `.env.example` en el puerto 3310:
  el 6.º `sign-in` en 60 s → 429; el techo por IP de `/auth/**` → 429 con sobre `RATE_LIMITED` y cabeceras `RateLimit`; el
  límite global → 429; `/health` nunca da 429, ni siquiera con el límite agotado.

## T14 — Usuarios, roles, permisos, auditoría y matriz RBAC completa (ola E2)

`tests/e2e/usuarios-roles.e2e.test.ts` y `tests/e2e/rbac.e2e.test.ts`:
- Usuarios (como superadmin y como ADMIN): crear (con y sin roles; sin roles → CONSULTA), el creado puede hacer login, listar
  (cursor y página, búsqueda, filtros) cotejado con la BD, ver, editar, `PATCH /users/me` (no acepta `status`: 422), poner
  roles, borrado lógico. Nunca aparece `password` ni hash en ninguna respuesta (comprueba el JSON completo).
- No-escalada por HTTP real: ADMIN no puede darse roles a sí mismo, no puede conceder SUPER_ADMIN, no puede administrar al
  superadmin; un usuario con solo `users:assign-roles` no puede dejar sin roles a un superior.
- Roles: listar, crear un rol `e2e-*` con permisos, editar, poner permisos (`*` → rechazado), los roles de sistema son
  inmutables, borrar un rol vacío.
- `GET /permissions`: exactamente el catálogo de `PERMISSION_LIST` agrupado.
- Auditoría: `GET /audit` con filtros (action, actorId, desde/hasta, cursor): aparecen las acciones de este archivo
  (`user.created`, `user.roles.set`, `role.*`...) con `actorEmail`; sin `userAgent` en la respuesta.
- **Matriz RBAC E2E:** un usuario por cada uno de los 7 roles (creado vía API). Para **todos** los endpoints públicos
  menos auth y assistant (sácalos de `registry.ts`), lo esperado se deriva de `SYSTEM_ROLES` y de los permisos que exige cada
  ruta (léelos de los `*.routes.ts`) → permitido (no 401/403) o 403. Sin sesión → 401 en todos. Las rutas mutantes que
  estén permitidas se ejercen con datos que no alteren a otros archivos (o con ids inexistentes que den 404 *después* de autorizar).

## T15 — Dashboard, analytics y cirugías con los datos reales, y CSV (ola E2)

`tests/e2e/dashboard.e2e.test.ts`, `tests/e2e/analytics.e2e.test.ts` y `tests/e2e/cirugias.e2e.test.ts`:
- Para cada endpoint (`/dashboard/summary|occupancy|wait-times|demand`, `/analytics/services|triage`, `/analytics/surgeries`):
  el periodo por defecto (30 días hasta la fecha de referencia) y un periodo explícito, cotejando **cada cifra** con una
  consulta independiente del test sobre la BD E2E: ingresos del periodo, camas físicas por unidad, censo en el instante de
  referencia, p50/p90 de espera por nivel, ingresos por día y unidad, `demandChangePct`, volumen por área y especialidad, top
  de procedimientos, distribución de triage, y los totales de cirugía (12.770 filas; `si/no/desconocido` = 2.216/1.048/9.506,
  y recálculalos también desde `data/raw/` en el test).
- La fecha de referencia devuelta = `max(admittedAt)`; la ocupación > 100 % aparece donde la BD lo dice; `insufficient_data`
  donde corresponde (0 camas físicas, prev7 = 0).
- Validación de query: `desde > hasta` → 422, rango > 366 días → 422, parámetro desconocido → 422, fecha inválida → 422.
- CSV (`/analytics/services|triage|surgeries/export`): `text/csv`, `Content-Disposition: attachment`, cabecera de columnas,
  mismo número de filas y mismos valores que el JSON equivalente, sin celdas que empiecen por `= + - @` sin neutralizar, y
  una fila de auditoría `data.export` por descarga; sin `analytics:export` (ANALISTA) → 403.
- Tiempos: cada endpoint < 1 s en E2E (mídelo y repórtalo).

## T16 — Medicamentos, stock y ciclo completo de alertas (ola E2)

`tests/e2e/medicamentos.e2e.test.ts` y `tests/e2e/alertas.e2e.test.ts`:
- `GET /medications`: paginación, `search` (incluido `%` literal: solo devuelve nombres que contienen `%`), `kind`
  medicamento/insumo cotejado con la BD; cantidades del periodo cotejadas; sin stock → `stock`, `daysOfInventory` y `risk` =
  `insufficient_data`; `rotation` siempre `insufficient_data`.
- `GET /medications/consumption`: serie diaria/semanal y top cotejados con la BD; por `code`.
- `GET /medications/critical` sin ningún stock → `status: 'insufficient_data'`. `PUT /medications/:code/stock` como
  FARMACIA: `daysOfInventory = stock / (consumo de 30 días / 30)`, cotejado; riesgo CRITICAL/LOW/OK en los umbrales exactos; aparece
  en `/critical`; auditoría `medication.stock.updated` con from/to; DIRECTOR → 403; code inválido → 422; cantidad negativa → 422.
- Alertas: `POST /alerts/evaluate` (FARMACIA y JEFE_SERVICIO sí, DIRECTOR no) → las alertas creadas cuadran con las métricas
  recalculadas en el test (ocupación > umbral, demanda, cirugía, y LOW_STOCK tras poner stock bajo); relanzar no duplica
  (`actualizadas`); subir el stock y reevaluar resuelve LOW_STOCK. Listado con filtros y cursor; **ámbito**: FARMACIA solo ve
  `medication`, DIRECTOR ve `service`, `triage`, `surgery` y `medication`; `GET /alerts/:id` fuera de ámbito → 404; PATCH
  OPEN→ACKNOWLEDGED→RESOLVED con auditoría; transición inválida → 409. Al terminar, restaura el stock (bórralo) y reevalúa.
